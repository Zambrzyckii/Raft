## Commands

Verified on .NET SDK 10.0.113:

- Build: `dotnet build Raft.sln`
- All tests: `dotnet test` (xUnit, 27 tests, takes ~40 s because of the integration tests)
- Fast tests only: `dotnet test --filter "Category!=Integration"` (23 unit tests, under a second)
- Integration tests only: `dotnet test --filter "Category=Integration"` (4 tests; each starts an in-process cluster and binds localhost ports in the 7101-7404 range)
- Single test class: `dotnet test --filter "FullyQualifiedName~ConsensusServiceTests"`
- Single test method: `dotnet test --filter "FullyQualifiedName=RaftServer.Tests.Services.ConsensusServiceTests.ProposeNumber_WhenNotLeader_Ignore"`
- Run the cluster: copy `.env.example` to `.env` once and `docker compose up -d postgres` first, then `dotnet run --project RaftServer` (8 nodes) or `dotnet run --project RaftServer -- 3` (3 nodes; a bare `3` without `--` is forwarded as well). Put `WaitForStart=true` in front (`WaitForStart=true dotnet run --project RaftServer`) to hold the search until the dashboard sends the start signal, the way compose runs it
- Run the dashboard gateway against a running cluster: `dotnet run --project RaftDashboard`, passing the cluster's node count the same way (`-- 3`, default 8). SignalR hub on `http://localhost:5100/hub/cluster`, port 5100 must be free, no database needed
- Run the dashboard UI in dev: `npm install` once in `dashboard/`, then `ng serve` there. UI on `http://localhost:4200`, `/hub` is proxied to the gateway (`dashboard/proxy.conf.json`, wired in `angular.json`), so the cluster and the gateway must be running
- Build the UI: `ng build` in `dashboard/` (output `dashboard/dist/dashboard/browser`)
- Containerised: `docker compose up --build`; the dashboard UI is served at `http://localhost:5100`. Compose sets `WaitForStart=true`, so the cluster elects a leader and waits for the start signal
- Pause and resume a node: click its circle in the UI, or `curl -X POST localhost:5100/api/nodes/4/pause` and `.../resume` (1-based index)
- Start the prime search on a waiting cluster: the `start prime search` button in the prompt line, or `curl -X POST localhost:5100/api/search/start` (502 when no node answers). Without `WaitForStart` the cluster searches from the start and the button never shows
- Change the search tempo: slider in the UI, or `curl -X POST localhost:5100/api/speed/200` (ms per checked number, clamped to 10-3000). The gateway keeps enforcing its current tempo on every node, default 800 ms, config key `WorkDelay` (clamped the same way); without a gateway the cluster runs at the code default of 50 ms, which is what the tests see

No linter or formatter is configured — there is no `.editorconfig`, `Directory.Build.props` or analyzer package. `Raft.sln.DotSettings.user` is a per-user Rider file, not a project-wide convention.

Startup side effects: before any node starts, the process connects to PostgreSQL and runs `CREATE TABLE IF NOT EXISTS primes` (`Program.cs:15-17`), so `dotnet run` fails fast when the database is down. Start it with `docker compose up -d postgres` (host port 5434). The connection string lives in `.env` in the repo root (gitignored, copy `.env.example`), loaded by `DotEnv.Load` (`RaftServer/Hosting/DotEnv.cs`) into the configuration before `AddEnvironmentVariables`, so real environment variables still win. The container image has no `.env`, compose assembles `ConnectionStrings__Primes` for it from the same file on the host. Ports 5001..500N must be free. Test clusters build their nodes without a storage instance, so `dotnet test` needs no database.

## Architecture

### One process is the whole cluster

`Program.cs:28-33` builds N `WebApplication` instances inside a single process through `NodeHost.Build` (`RaftServer/Hosting/NodeHost.cs`), each with its own DI container and its own `RaftNode` singleton (`NodeHost.cs:25`). A node's identity is its URL, `http://localhost:500{i}` (`Program.cs:25`), and its peer list is simply every other URL (`NodeHost.cs:14-21`). By default Kestrel binds the identity URL itself, so host runs and tests stay on loopback; setting `BindHost` (read in `Program.cs:19`, compose sets `*` for the container) rebinds that host on the port taken from the URL (`NodeHost.cs:23-24`) without changing the node identity, which is what lets the gateway container reach the nodes. All nodes share one `PostgresStorageService` over one `NpgsqlDataSource` created in `Program.cs:15-16` and passed into `NodeHost.Build` as an optional parameter. There are no per-node config files and no service discovery. The integration tests build their nodes with the same `NodeHost.Build` (`RaftServer.Tests/Cluster/TestCluster.cs`) but omit the storage argument, so test clusters run the production wiring minus persistence.

Consequence: `compose.yaml` starts **one container that contains the entire cluster** plus a `postgres` and a `dashboard` service. Scaling the raft service with `replicas` would not add nodes, it would start additional independent clusters. The Dockerfile's `EXPOSE 8080/8081` is inert because `UseUrls` (`NodeHost.cs:24`) overrides it; the published ports are PostgreSQL's 5434 and the dashboard's 5100, the only two windows into the cluster from the host. Compose sets `BindHost=*` for the raft service, so the node ports are reachable from other containers on the compose network (the dashboard polls them as `http://raft:500{i}`) but not from the host.

### Three concurrent writers per node

Each node runs up to three `BackgroundService`s — `RaftEngine` (consensus), `MathEngine` (prime search) and `StorageEngine` (PostgreSQL batch writer, registered only when `NodeHost.Build` received a storage instance, so never in tests) — plus the gRPC handlers in `ConsensusService`. All of them share the same `RaftNode` instance, which is the only coordination point. Locking is per-field and not uniform: `lock (_node)` (`ConsensusService.cs:58`), `lock (OfficialPrimes)` (`ConsensusService.cs:27`, `VoteCounter.cs:14`, `ReliableProposer.cs:44`, `StorageEngine.cs:28`), `lock (pendingNumber)` (`ConsensusService.cs:40`, `Leader.cs:15`), while some reads of the same collections are unlocked (`Leader.cs:25`, `MathEngine.cs:25`). Assume any `RaftNode` field can change underneath you.

### Role transitions (State pattern)

`RaftEngine.ExecuteAsync` (`RaftEngine.cs:32-43`) swaps the `IRaftState` object whenever `RaftNode._currentState` no longer matches the current one, then calls `Execute` in a tight loop. A paused node skips the whole loop (`RaftEngine.cs:26-30`), so it neither acts on its role nor times out into an election. The role is set from three directions: by the role behaviours themselves (`Follower.cs:24`, `Candidate.cs:82`, `Candidate.cs:88`), by incoming RPCs (`ConsensusService.cs:23`, `ConsensusService.cs:66`), and by a leader that sees a newer term in an ack and steps down and ends the turn (`TermGuard.cs`, called from `Leader.cs:38` and `Leader.cs:85`).

The election timeout is not a timer: a follower awaits `Task.Delay(2000-4000, token)` (`Follower.cs:11-15`) and an incoming heartbeat cancels that token through `RaftNode.CancelTokenTimeout()` (`RaftNode.cs:26`, called from `ConsensusService.cs:21`). A heartbeat with a stale term is rejected without resetting the timeout (`ConsensusService.cs:18-19`). `Timer/RandomTime.cs` is dead code and says so in its own comment.

**Debugging note**: `RaftEngine.cs:45-53` catches *every* exception thrown by a role's `Execute`, logs the role, exception type and message, and sleeps 2 s. A recurring `... failed: ...` line in the console is a role crashing on every iteration, not a slow cluster.

### Prime commit path (the part that spans the most files)

1. `MathEngine.cs:18` — only an unpaused follower that already knows its leader and is not waiting for the start signal (`RaftNode.waitingForStart`, see the gRPC layer) computes; each node walks its own `_currentNumber` counter, pacing each checked number with `Task.Delay(workDelay)` (`RaftNode.workDelay`, default 50 ms, set remotely through the monitoring `SetSpeed` RPC).
2. `DynamicWorkDivider.IsMyTurn` (`DynamicWorkDivider.cs:9-21`) — sharding by `number % followerCount == myIndex` over the sorted peer list with the current leader removed, so work rebalances by itself after every leader change.
3. `IsPrime.CheckPrime` (`Algorithm/IsPrime.cs`) — 6k±1 trial division.
4. `ReliableProposer.SendAndWaitForAckAsync` (`ReliableProposer.cs:16-52`) — resends `ProposeNumber` every 200 ms, re-resolving `context.currentLeader` on each retry (so a leader change mid-proposal is followed), until the number appears in the node's own `OfficialPrimes`; that local arrival (delivered later by `AppendEntries`) *is* the acknowledgement.
5. Leader side: `ConsensusService.ProposeNumber` (`ConsensusService.cs:35-54`) deduplicates against the log and the queue, then enqueues into `pendingNumber`; a non-leader answers `IsFine = false`.
6. `Leader.Execute` (`Leader.cs:11-58`) peeks one queued item, replicates it with `ProposeNumbers.SendProposeNumbers`, steps down and returns if an ack carries a newer term (`TermGuard.cs`), counts non-null `IsDone` acks and requires a majority in `VoteCounter.cs:8-22`, appends a `LogEntry` stamped with `currentTerm` (`VoteCounter.cs:18`), and only then dequeues.
7. With an empty queue the leader sends heartbeats instead (`Leader.cs:59-89`), and paces every iteration with `Task.Delay(50)` (`Leader.cs:91`).
8. Persistence is asynchronous and decoupled from consensus: the leader's `StorageEngine` snapshots `OfficialPrimes` under its lock every 500 ms and, once at least 50 new entries accumulated, writes exactly 50 of them with `INSERT ... ON CONFLICT (number) DO NOTHING` in one transaction (`StorageEngine.cs:25-38`, `PostgresStorageService.cs:29-46`). `_savedCount` advances only after a successful write, so a failed batch is retried; a new leader resends its whole log from index 0 in chunks of 50, which the unique index absorbs; the tail below 50 entries is never written. `found_by` and `search_time` travel from the proposal through `LogEntry` (`VoteCounter.cs:18`) and are NULL on entries a node learned over `AppendEntries`, because `AppendRequest` does not carry them and `ON CONFLICT DO NOTHING` keeps the first written row. `FileStorageService` has no callers anymore and remains as dead code.

Replication is set-based, not index-based: a follower appends any number it has not seen from `AppendEntries` (`ConsensusService.cs:25-31`); there is no log matching or backtracking. A request whose `LeaderTerm` is lower than the node's term is denied with `IsDone = false` and the node's own term in `AppendResponse.Term` (`ConsensusService.cs:18-19`). The election restriction is approximated by comparing log count and last term (`ConsensusService.cs:69-76`).

### gRPC layer

The consensus contract lives in `Protos/RaftConsensus.proto`, generated for both client and server (`RaftServer.csproj:12`) into namespace `Raft.Grpc`. `AppendResponse` carries the responder's term (`RaftConsensus.proto:31`), which is what `TermGuard` reads. A second, read-only contract `Protos/RaftMonitoring.proto` (`RaftServer.csproj:13`) exposes `GetStatus`, `SetPaused`, `SetSpeed` and `StartSearch` for the dashboard gateway, served by `MonitoringService` (`RaftServer/Services/MonitoringService.cs`, mapped at `NodeHost.cs:39`). Every interesting step of the algorithm also emits a `NodeEvent` (`found`, `propose`, `received`, `replicate`, `committed`, `timeout`, `campaign`, `vote`, `won`, `lost`, `paused`, `resumed`) into a 200-entry ring buffer on the node (`RaftNode.AddEvent`), and `GetStatus` returns the events newer than `StatusRequest.sinceSeq` together with `lastSeq`, which is how the gateway streams them exactly once. It is deliberately a separate service so the chaos interceptor can block consensus calls without blinding monitoring: `ChaosInterceptor` (`RaftServer/Services/ChaosInterceptor.cs`) is registered only on `ConsensusService` (`NodeHost.cs:31-34`) and answers every consensus call with `Unavailable` while `RaftNode.paused` is set, which the callers' `*Safe` helpers read as a dead peer. ASP.NET Core logs every such `RpcException` at Information, which for a paused follower means about 20 lines a second from the leader's heartbeats, so `appsettings.json:6` raises the `Grpc.AspNetCore` category to Warning. Real handler failures still log at Error. A resumed node keeps the log gap from its pause, because `AppendEntries` carries only new commits. `StatusResponse.currentLeader` is assigned only when `AppendEntries` arrives (`ConsensusService.cs:24`) and never cleared on becoming leader, so on the leader itself it holds the stale address of the previous leader it served under, or stays empty after a first clean election — infer the leader from `role`, not from this field. Plaintext HTTP/2 is forced in `appsettings.json:10-14`; gRPC will not work without it. The test host copies that `appsettings.json` next to the test binaries, which is why in-process test clusters get HTTP/2 without extra configuration.

A cluster started with `WaitForStart=true` (read in `Program.cs:20` and passed through `NodeHost.Build` like `BindHost`, compose sets it) creates every `RaftNode` with `waitingForStart` set, and `MathEngine.cs:18` does not search while it is set. Elections and heartbeats run as usual, so the dashboard shows a cluster that has a leader and waits. `StartSearch` clears the flag once and logs `Search started from the dashboard`, and `GetStatus` reports it as `waitingForStart`. No RPC sets it again, so only a restarted cluster waits again. Without the setting the flag is never set, which keeps host runs and the test clusters searching from the start.

Channel reuse is deliberate (socket exhaustion was a real problem in this project) but partial: `Leader._channelCache` (`Leader.cs:10`, per Leader instance, so it resets on every role change) and the static `ReliableProposer._channels` (`ReliableProposer.cs:10`) cache channels, while `Candidate.FarmVoteResponses` (`Candidate.cs:63`) still creates a fresh channel per peer per campaign.

### Dashboard gateway

`RaftDashboard/` is a second web app in the solution that turns the monitoring contract into a browser feed; it has no database and reads no `.env`. `ClusterPoller` (`RaftDashboard/Services/ClusterPoller.cs:23-33`) polls `GetStatus` on every node in parallel every 500 ms and broadcasts one `ClusterSnapshot` to all SignalR clients as the `ClusterState` event on the `/hub/cluster` hub (`RaftDashboard/Program.cs:41`). The poller keeps a `sinceSeq` cursor per node, so each broadcast carries only that node's new events. A `lastSeq` below the cursor means the node was restarted, so the poller asks it again from zero in the same round (`ClusterPoller.cs:42-46`). A restart goes unnoticed only when the new node has already recorded more events than the old cursor by its first successful poll. The poller also re-pushes the desired tempo with `SetSpeed` whenever a node reports a different `workDelay` (`ClusterSpeed` singleton, default 800 ms, config `WorkDelay`, clamped to 10-3000 in `RaftDashboard/Program.cs:19-21` like the REST endpoint), which also heals a restarted cluster. The `GrpcChannel` per node lives in `NodeClients` (`RaftDashboard/Services/NodeClients.cs`), shared for the gateway's lifetime between the poller and the REST endpoints. A dead node does not fail the round: `GetStatusSafe` (`ClusterPoller.cs:35-66`) turns a 1 s deadline or any error into `online = false`, mirroring the server's `*Safe` convention. REST: `POST /api/nodes/{index}/pause` and `/resume` (`RaftDashboard/Program.cs:42-43`, 1-based index, 404 for an unknown one, 502 when the node is unreachable) call `SetPaused`, and `POST /api/speed/{delayMs}` (`Program.cs:44`) updates `ClusterSpeed` and fans `SetSpeed` out to every node, and `POST /api/search/start` (`Program.cs:45`) fans `StartSearch` out to every node and answers 502 only when none of them accepted it. Unlike the tempo, the gateway keeps no start state, so a restarted cluster waits for a new start signal. `ClusterHub` stays deliberately empty — the browser only listens on it.

Node addresses are built the same way the cluster builds them, `http://{NodeHost}:500{i}` with the count from `args[0]` (default 8, `RaftDashboard/Program.cs:12-17`); `NodeHost` defaults to `localhost` and compose sets `raft`, which is what `BindHost=*` on the raft service exists for. `GatewayUrl` (default `http://localhost:5100`, `RaftDashboard/Program.cs:10`) sets the bind address, compose sets `http://*:5100` and publishes the port. The proto is linked from `RaftServer/Protos/RaftMonitoring.proto` (`RaftDashboard.csproj:11`), which is why `RaftDashboard/Dockerfile` builds with the repo root as context (`compose.yaml`), unlike `RaftServer/Dockerfile` which builds from its own directory. The project uses the default `RaftDashboard.*` namespaces, not the server's `Raft.*`.

The browser UI is an Angular app in `dashboard/` (Angular CLI 22, zoneless, signals, JetBrains Mono, an amber on black terminal look). The `Cluster` service (`dashboard/src/app/cluster.ts`) owns the one `HubConnection` (relative URL `/hub/cluster`, unbounded 2 s reconnect retry). It exposes the last `ClusterSnapshot` as a signal and every snapshot as the `snapshots` observable, because a signal can coalesce two quick snapshots and lose a batch of events. It also sends the pause, resume, tempo and start commands and keeps their `[OK]` or `[ERR]` result for 3.5 s in the `notice` signal. Its `waiting` signal is true while an online node reports `waitingForStart` and no start request of this page still awaits confirmation from a snapshot. The `Header` component (`dashboard/src/app/header.ts`) renders the inverted status bar, the `raft@cluster:~$` prompt line that echoes those results and reports a lost gateway connection, and the tempo slider with 11 non-linear steps from 2000 to 100 ms. While the cluster waits, the prompt line holds the `start prime search` button, which disappears on click and comes back only when the request fails or a restarted cluster waits again. The `App` component (`dashboard/src/app/app.ts`) renders the scene. Followers and candidates sit on a dashed orbit, the active leader (online, unpaused, role `Leader`, highest term) is pulled to the centre with a glowing amber outline, and role changes glide because node positions are CSS-transitioned. The geometry lives in `layout.ts`, and the stage is the largest square that fits under the header and still leaves room below the bottom node for its feed (container query units). Clicking a circle pauses or resumes that node. Only the circle takes pointer events, because on small stages a node's feed overlaps the circles next to it. A paused or offline node fades only its circle, so its term, log and status tag keep their contrast. The `Backdrop` component (`dashboard/src/app/backdrop.ts`) draws on a fixed canvas behind the page, placed outside `.arena` because its `container-type: size` would become the containing block of a fixed element. Dots of the CSS dot grid that the pointer passes over light up and fade within about a second, the draw loop runs only while a dot glows, and the effect stays off under `prefers-reduced-motion` and on devices without hover. `public/favicon.svg` is a 16 by 16 pixel art terminal, and `favicon.ico` carries the same image for browsers without SVG icons.

Event playback lives in the `Playback` service (`dashboard/src/app/playback.ts`). It plays node-side events first with a short stagger, then holds the leader's `received` and `replicate` for a number until the proposal shot has landed and `committed` until the replication shots have landed, so the order reads right even though all three usually arrive in one 500 ms batch. Each node keeps one feed line per number (and per election term) whose status changes in place, and lines fade after 8 s. Shots, commit rings and found halos are signal arrays rendered from the template and removed on `animationend`. Creating them with `document.createElement` breaks their styles, because emulated view encapsulation scopes component CSS to `_ngcontent` attributes that such elements never get. Batches above 60 events (a gateway restart replays every ring buffer) and batches arriving in a hidden tab are skipped, and `prefers-reduced-motion` disables shots, rings, halos and transitions.

In dev the UI runs on `ng serve` and the proxy forwards `/hub` and `/api` to the gateway, so there is no CORS anywhere. In the container the gateway serves the built app itself: `RaftDashboard/Dockerfile` builds it in a `node:26-alpine` stage and drops `dist/dashboard/browser` into `wwwroot`, and `RaftDashboard/Program.cs:33-39` enables static files plus an `index.html` fallback only when `wwwroot/index.html` exists, so host runs of the gateway stay API-only.

## Conventions

- `RootNamespace` is `Raft` (`RaftServer.csproj:8`), so folders map to `Raft.*`, not `RaftServer.*` — `RaftServer/Services/` → `namespace Raft.Services`. Test namespaces are `RaftServer.Tests.*`.
- Model members are camelCase, some with a leading underscore (`RaftNode.currentTerm`, `RaftNode._currentState`), and role behaviours name their parameter `_context`. Unusual for C#, but match it.
- Role logic longer than a few lines is extracted into a static helper class next to the role (`RoleBehaviours/Leader/ProposeNumbers.cs`, `VoteCounter.cs`, `GetSignal.cs`, `TermGuard.cs`).
- Remote calls go through `*Safe` helpers that swallow the exception and return `null` (`GetSignal.cs:9-16`, `Candidate.cs:31-41`). A `null` means a dead peer, and callers count only non-null responses (`Candidate.cs:26`, `Leader.cs:46`).
- Tests: xUnit, `Method_Scenario_Expectation` naming; `ConsensusService` is exercised directly with `null!` as the `ServerCallContext` (`ConsensusServiceTests.cs:15`).
- Integration tests (`RaftServer.Tests/Cluster/`) carry `[Trait("Category", "Integration")]`, share one xUnit collection so clusters never run in parallel, use a fixed port range per test, and wait on conditions with a timeout (`TestCluster.WaitUntilAsync`) instead of fixed delays.
- Code, comments and commit messages are written in English.

## README vs code

`README.md` describes 8 independent processes; in reality it is one process hosting 8 in-process Kestrel servers, and one Docker container. It also states that gRPC channels are created once and cached — true for the leader and proposer paths, not for the election path (`Candidate.cs:63`).
